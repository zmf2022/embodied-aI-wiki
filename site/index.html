SIM-TO-REAL为什么 BAM 比简单的随机化更值得关注？

Better Actuator Models（BAM）· 执行器模型

仿真策略可以学到漂亮动作，但实际电机存在命令延迟、传动回差和共享电池电压下降。BAM 通过更真实的执行器响应模型减少“控制指令 ≠ 实际运动”的偏差。

  • Servo 命令响应与延迟
  • 机械背隙与死区
  • 电池电压变化带来的驱动力差异

Domain Randomization · 分布覆盖

对接触、传感噪声及物理参数做受控扰动，让策略在现实变化下具有韧性；前提是扰动范围合理，否则可能训练出不符合真实任务的行为。

  • 地形与摩擦变化
  • 观测噪声与传感偏差
  • 真实硬件测试后反向校准参数
证据边界：NVIDIA 博客详细展示了资产生成、Isaac Lab 并行训练、RTX Spark 上的仿真评测和为实体部署做准备的流程；详细的硬件部署步骤明确不在该文章范围。文中展示实体 Microduck 行走结果，但不应由此推断所有策略或机器人本体均可直接迁移。

05

Isaac Lab 3.0：从单一仿真训练走向多后端基础设施

ARCHITECTURAL SHIFT

这次的重大变化不是新增几个任务，而是重新组织底层：机器人资产、物理引擎、渲染、数据路径与可视化可以相对独立选择。

PHYSICS

多后端物理

统一接口支持 PhysX、Newton/MJWarp 等后端；不同后端的任务和接触特性仍有兼容性边界。

RUNTIME

Kit-less 模式

部分训练不再必须完整启动 Isaac Sim Kit；适合高吞吐、非高保真渲染的物理学习实验。

MEMORY

Warp / ProxyArray

增强 GPU 原生数据路径，减少多层张量搬运；不等于所有自定义 PyTorch 算法无需适配。

RENDER

渲染与可视化解耦

分离物理、渲染和可视化后端，使纯训练、高保真传感器仿真和远程观察有不同的成本组合。

BENCHMARK

统一训练/评测接口

启动、运行时与训练 Benchmark 更规范，有利于在相同设置下比较不同后端。

AGENT READY

工具可编排

与 Agent Skills 和配置体系配合，让自动生成任务、调试和调用评测工具更可行。

洞察三：未来 Benchmark 的关键不是“哪个仿真器最流行”，而是统一任务语义下的可复现性。

同一任务在不同物理引擎下的接触解、传感器模型和数值参数可能不同；迁移不应默认成功率具有可比性。

工程注意：从 Isaac Lab 2.x 升级 3.0 涉及四元数 WXYZ → XYZW、Tensor → ProxyArray、数据访问与写入 API 的变化。独立迁移分支应先通过坐标、接触、观测维度、奖励和动作时序的回归验证。

POST-TRAININGGR00T 1.7、Cosmos 与专业技能的三个工作流

① 通用策略 → GR00T 1.7 RL 精炼

利用 Isaac 仿真反馈和强化学习改进预训练策略的技能表现。必须明确评测任务、训练预算和是否真正提升未知场景的泛化。

② Isaac Lab 灵巧操作训练

把接触丰富、需要多指控制的操作任务放到可并行模拟的物理环境中学习，关注接触稳定性、重规划和失败恢复。

③ Cosmos 世界模型后训练

面向合成视频/世界数据生成，借助 Agent 工作流形成候选场景；需要做空间关系、交互一致性和训练收益验证。

数据的有效性边界

SimReady 资产 ≠ 自动具有任务级物理可信度；Human 1M 的完整数据存在合作伙伴访问限制；合成数据的数量也不能代替真实任务成功率。

洞察：数据引擎的下一步是「有目标的数据生成」。

比随机扩增图像更有价值的是：识别失败模式 → 生成具备物理边界的扰动 → 重新训练 → 在冻结的未见测试集上验收。

TWO SAFETY LAYERSOpenShell 与 Halos：Agent 安全 ≠ 机器人实体安全

OpenShell · Agent 权限与运行隔离

安全必须在 Agent 进程外实施，而不是依赖模型承诺“不会做危险操作”。OpenShell 的关键组件：

  1. Gateway：管理沙箱与策略生命周期
  2. Supervisor：检查外部访问并代理凭据
  3. Sandbox：隔离文件系统、进程和网络
  4. Policy Prover：验证权限不超过组织上限

参考架构结合 Vera CPU 运行 Agent Harness、Vera Rubin 推理，以及 BlueField-4/Sentry 外部监控。

Halos · 实体机器人风险控制

聚焦物理行为、设备运行和可证明的安全边界。实体机器人系统应另外具备：

  1. 接触/速度/力/空间安全约束
  2. 危险动作拦截与失效模式处理
  3. 人机共处监控、人工接管
  4. 硬件安全链路及审计记录

两种安全架构可组合，但不应把 OpenShell 当成安全 PLC 或硬实时伺服替代品。

洞察：安全能力已从上线前测试，前移到 Agent 的每次工具调用和机器人的每次物理执行。

管理研发 Agent 修改代码的权限，与管理实际机器人动作的安全边界，应由不同层级分别实施。

核心研发方向：Agentic Robot Learning · 让机器人技能主动进化

CODING AGENT × SKILL DISCOVERY × TRAINING × INDEPENDENT EVALUATION

Code-as-Policy 是一种技能实现方式，Agentic Robotics 是更广的机器人智能体架构；Agentic Robot Learning 更准确地表达「让 Codex / Claude 自主探索、编码、仿真训练、验证、积累技能」的研发目标。建议平台研究名沿用 Embodied Autoresearch，最终评价目标为 Self-Improving Robot Skills。不要将生成脚本、重新训练神经策略和测试时重新规划混为一谈。

ONLINE / EXECUTION

Code-as-Policy

研究 Agent 修改训练配置、奖励、数据/策略代码，运行 RL/BC/VLA 微调并在独立任务中检验收益。

Worken：从演示成功率到有效智能工时

ROBOT ECONOMICS / QUALITY-ADJUSTED AUTONOMY

Worken = N × T × η活跃机器人数量 × 自主工作时长 × 产出效能比
N · ACTIVE

活跃本体数量

不是出货量或安装量；必须确实执行业务任务。

T · TIME

有效自主时长

扣除待机和人工持续遥操作，需记录中断与恢复。

η · OUTPUT

产出效能比

相对特定岗位合格作业基准，不是简单乘以任务成功率。

Worken 是厂商提出的产业评价框架，还不是跨场景统一的审计和结算标准。必须与作业质量、安全事件、人工接管、维护/算力成本等指标共同使用；不能以仿真 99.8% 操作成功率直接换算真实 Worken。
